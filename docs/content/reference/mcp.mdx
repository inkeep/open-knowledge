The MCP server gives AI agents structured access to your knowledge base. A few tools answer without a running server: `exec` (fs-direct shell reads straight off the disk — only the backlink and forward-link enrichment needs the server; history comes from the shadow repo on disk), plus `config` and `palette`. `preview_url` resolves from the project's lock files, but treats opening a preview as demand: if no server is running it auto-starts one (under the `OK_MCP_AUTOSTART` gate).

Every other read tool (`search`, `links`, `history`, etc.) and all write tools route through the Hocuspocus server, which OpenKnowledge auto-starts on the first call that needs it, under the same `OK_MCP_AUTOSTART` gate. Routed stdio calls use `cwd`, an absolute project or worktree path: it is required until a project is selected unless the client advertises exactly one root. Project-bound HTTP calls may omit `cwd` and stay confined to their configured root. The `exec` tool also uses `cwd` as its read command's directory.

The surface is **19 tools**. The four write verbs — `write`, `edit`, `delete`, `move` — are native CRUD operations polymorphic over a target. `write`, `edit`, and `delete` nest per-target fields inside the address key (`write({ document: { path, content } })`) and take exactly one target per call: `document`, `folder`, `template`, or `skill` — plus `asset` for `write` and `delete`, and a `documents` batch on `write` that writes several docs in order, each entry carrying its own `summary`. `move` takes flat `from`/`to` paths and auto-detects a document, folder, or asset, with nested `template` and `skill` targets for those two.

To point an MCP client at this server, locally or over a tunnel from another machine, see [Connect remote agents](/docs/remote-control/connecting-agents).

Successful responses include `ran`: enabled document-lint families plus `links` unless link validation is off. Document and project-tree OKF checks share the `okf` family, and a family absent from `ran` was not checked. Same 10 × 10 output cap as `lint`'s audit, plus a warning cap set project-wide at 10 warnings, with accurate totals and `omittedWarningCount` when warnings are dropped. Use `skill` to choose one skill from a multi-skill source or a `skills({ query })` result. | `checkpoint` | Save a project-wide version snapshot — a single restore point. Returns its `version` |
| `restore_version` | Restore one `document` or `skill` to a historical `version` (the SHA from `history` or `checkpoint`) |

## Audit scopes and complete results

The `path` scope for `audit` and project-wide `lint` selects an existing file or directory first. If a document stem without `.md` or `.mdx` does not exist, OpenKnowledge tries `.mdx` before `.md`; an explicitly supplied document extension must exist as written. An unknown scope returns a not-found error naming the path and how to correct it. An existing empty or ignored scope reports zero documents checked and an informational warning, rather than implying the content passed validation. The CLI equivalents, `ok audit` and `ok lint`, share these path-resolution rules: unknown scopes exit 1 (before any `--fix` write), while valid zero-document scopes exit 0. `audit`, project-wide `lint` and server-backed `ok audit` refuse hidden-segment scopes: zero documents are checked and the refusal is an ordinary warning, not the informational empty-scope one (`ok audit` exits 0). Headless `ok lint` checks them when explicitly named.

Narrowing `path` reduces competing files, but does not lift per-file caps. Use `lint({ document: "guides/intro" })` for all document-lint findings, and `links({ kind: "dead", sourceDocuments: ["guides/intro"] })` for raw unresolved links from that document. Project-tree OKF findings in MCP audit results remain capped. Diagnostic totals always cover the full scan.

## Output shape mirrors the input

The write verbs nest their result under the same target key you wrote, mirroring the input: `write({ folder })` returns `{ folder: { ok, path } }`, `edit({ document })` returns `{ document: { … } }`, and a batch returns `{ documents: [ … ] }`. The preview envelope (`previewUrl`, `previewUrlSource`, `warning`) stays at the top level on `write` and `edit` responses; read tools (`search`, `links`, `exec`) attach a route-only `previewUrl` to each hit or entry instead. `links` nests the same way under its `kind`.

## Advisory warnings

`write` and `edit` results may carry a `warnings` array on the document entry (per entry for a batch); `restore_version` carries it at the top level. Entries are discriminated by `kind`. `content-divergence` and `disk-edit-reconciled` are write-integrity signals — the stored doc differs from what the call composed, so re-read it before editing further. A `disk-edit-reconciled` entry carries `mergeOutcome`, one of `clean` (the outside edit was taken as is), `merged` (both sides' edits were merged), `both-kept` or `kept-live`. `both-kept` means an outside edit and edits made in OpenKnowledge changed the same blocks, and three counts say what landed: `duplicatedBlocks` blocks are in the document twice, the OpenKnowledge version first and the outside version directly under it; `restoredDeletedHere` blocks deleted in OpenKnowledge came back with the outside version because the outside edit changed them; `restoredDeletedOutside` blocks the outside edit deleted stayed with the OpenKnowledge version because they were changed there. `kept-live` means the outside edit could not be merged, so the OpenKnowledge version stayed and the outside version was saved to the document's history. Those two outcomes also carry `nextStep: "re-read"`. In both the write landed and should not be retried; after `both-kept`, remove a duplicate, or delete a block restored over a deletion in OpenKnowledge, with an ordinary edit if the task calls for it. `mergeOutcome` and `nextStep` can gain values; treat a value you do not know like `merged`: the write landed, re-read the document. `mermaid-parse-error` means the write landed but that fence won't render — fix the fence and re-edit. `lint-violation` reports a content-rule finding at a line and column. `link-check-deferred` means the server was still building its link index after starting, or the index was busy with other writes, so links were not checked and an empty `brokenLinks` is not an all-clear; that document's links are checked again only when it is written or edited later, or by an `audit`, which can time out until startup finishes.

`delete`, `move` and `install` on a `skill` target carry a separate `warnings` array of plain strings, not `kind`-discriminated entries. It reports work that did not undo the operation: bookkeeping records the server could not update after the skill itself was already deleted, renamed or moved, and — on a delete — that the directory removed was one an earlier failed move had retained for recovery. The operation succeeded; the warning names what to check or repair.

## Instantiating from a template

`write` accepts a `template` field on the `document` target — `write({ document: { path, template } })` — that resolves against the cascade of templates available for the target document's parent folder, using the same folder-up walk the [Folders and templates](../advanced/folders-and-templates.mdx#templates) page describes. The template body becomes the new document's content; the template's own info block (its name and description) is stripped, so it doesn't bleed onto the document.

`content` and `template` are mutually exclusive. With `template`, `position` is forced to `replace` (initial create semantics).

## Editing frontmatter

Use `edit({ document: { path, frontmatter } })` for frontmatter edits: it applies a top-level merge patch (set or create a key with a value, delete a key by passing `null`; a nested object replaces that key's whole subtree, and `null` inside a subtree is rejected). A document body find/replace (`edit({ document: { path, find, replace } })`) is body-only and refuses patterns that touch frontmatter; `write` with `position: "replace"` is the only write mode that includes the `---\n…\n---` block (other positions ignore any frontmatter in the payload). Folders and templates take frontmatter the same way: `edit({ folder: { path, frontmatter } })`.

## Edit summaries

The write tools (`write`, `edit`, `move`, `install`, `checkpoint`, `restore_version`) accept an optional `summary` describing the intent of the edit, e.g. `"Fixed token-refresh race"`. Summaries appear on the document's timeline so readers can scan recent agent activity.

Cap is 80 characters. Avoid secrets and PII; summaries persist to git history.

## Markdown input admission

New Markdown text rejects decoded C0 controls U+0000–U+001F except TAB (U+0009), LF (U+000A), and CR (U+000D). Remove unsupported characters or replace them with printable escapes such as literal `\u0000`. Printable escapes, DEL, C1, and other admitted Unicode are preserved; binary assets and non-Markdown bundle files are not covered by this rule.

The shared HTTP request schemas guard these nine fields before any write, rename, agent session, or contributor mutation:

| HTTP input field | MCP surface |
| --- | --- |
| `POST /api/agent-write`: `content` | HTTP-only document text input |
| `POST /api/agent-write-md`: `markdown` | `write.document.content`, including frontmatter composition or template expansion |
| `POST /api/agent-patch`: `replace` | `edit.document.replace`; `find` remains unrestricted |
| `POST /api/agent-write-batch`: `docs[i].markdown` | Direct HTTP batch; MCP `documents` uses separate writes |
| `PUT /api/template`: `body` | `write.template.content` and reconstructed template edits |
| `POST /api/template`: `body` | Supplied replacement body on an HTTP move |
| `PUT /api/skill`: `body` | `write.skill.body` and reconstructed skill edits |
| `POST /api/skill`: `body` | Supplied replacement body on an HTTP move |
| `PUT /api/skill-file`: `content` | `write.skill.files[i].content` and reconstructed file edits, when the writer's normalized final path segment has a case-insensitive `.md`/`.mdx` suffix |

Markdown bundle admission applies in project and global scope, including Markdown files under `scripts/` or `assets/`; the inferred file kind does not exempt them. Backslashes become slashes, and empty or `.` segments are removed before this decision; MCP forwards the resolver's canonical path. Other suffixes, including `.md.bak`, remain opaque.

A refusal returns HTTP 400 with problem type `urn:ok:error:invalid-request` and server-derived extension `contentControlAdmission: true`. This extension is derived from the control validator's issue metadata, not from echoed input or error-message text; unrelated validation errors do not carry it. Its detail names the field, first offending code point (for example `U+0000`), and **zero-based UTF-16 code-unit offset in that submitted field**, without echoing content. Each invalid field gets its first issue; an invalid HTTP batch may report multiple indexed issues. MCP returns a tool error retaining those details and the remove-or-printable-escape remedy. A document write's `markdown` offset can refer to composed Markdown **including frontmatter**, or generated template Markdown **after substitution**, not just the supplied body. Template and skill offsets refer to the whole submitted `body`; bundle-file offsets include the whole file, including YAML frontmatter.

Existing stored bytes are not rewritten. Document body `find` may match historical controls, and a clean `replace` can repair one occurrence without removing unrelated historical bytes; clean append/prepend deltas, loading, undo, and restore do not rescan old content. HTTP template/skill moves that omit `body` preserve the historical body.

Template metadata/body edits and skill description/body edits through MCP resubmit a full body. Markdown bundle edits resubmit the whole file. These calls refuse while any unsupported historical control remains in that payload, even if the requested edit only changes metadata or repairs another occurrence. Submit a fully cleaned replacement with the required template/skill metadata instead. A NUL-containing bundle file also hits the existing HTTP 415 binary-read refusal before MCP can perform find/replace; use a known complete clean file replacement.

### Batch admission and retries

`POST /api/agent-write-batch` validates the whole request before processing. One invalid entry rejects the request with 400 and **no sibling writes**. After validation succeeds, runtime failures retain per-entry outcomes and partial success.

MCP `write({ documents: [...] })` writes entries sequentially and returns ordered results with an overall tool error if any fails. Successful entries before and after a refused entry stay written. MCP `skill.files` similarly aggregates sequential per-file outcomes. Retry only failed entries after correcting the input; do not resend successful siblings.

## Conflict-aware writes

A doc can land in conflict through a Git merge, a pull that collides with a local overlay, or OpenKnowledge's own reconciliation of the editor against disk. Reconciliation covers `stale-external-write`, which protects an acknowledged edit when another app restores the exact older file version, even with GitHub sync disabled. Every mutating tool (`write`, `edit`, `delete`, `move`, `restore_version`, and agent undo) refuses a conflicted doc with an RFC 9457 problem response (409) that names the kind and the strategies that apply to it:

```json
{
  "type": "urn:ok:error:doc-in-conflict",
  "title": "Document is in conflict.",
  "status": 409,
  "detail": "The document is in a conflict state. Ask the user to resolve it in the OpenKnowledge app, then retry.",
  "file": "notes/sso.md",
  "conflict": { "kind": "reconcile", "reason": "disk-markers" },
  "resolutionOptions": ["mine", "content", "delete"]
}
```

A write that first detects the stale file during its final disk flush returns a different 409, `urn:ok:error:stale-external-write`. The edit reached collaborative state and the recovery snapshot, but the disk write did not happen. Ask the user to resolve the conflict, then re-read the document. Do not repeat the operation: compare the resolved content with the intended result and make only any remaining edit.

When OpenKnowledge saves a Markdown document, it first compares the file with the version it last agreed with the disk. If another tool changed the file, that change is merged into the document before the save, so the write succeeds and the file holds both edits; re-read the document before editing it further. This covers saves of edits made in the app, idle saves, the save at quit, the in-app agent's whole-document write and the agent write routes. Rename, delete and the other writers do not run this comparison yet. The stale-external-write case above is the exception: when the file holds a version that an earlier agent write replaced, the write returns that 409 instead. If a Markdown save cannot finish safely, the write returns `urn:ok:error:save-held` (503). The body carries `reason` (what holds the save), `retryWhen` (what the server's own save waits for; it is never a cue to repeat the request) and `nextStep: re-read`; in a batch response the same fields appear on that entry's `error`. When the file cannot be read (`pending-unreadable`, with the errno in `causeCode`), keeps changing (`pending-exhausted`, `pending-base-moved`) or the outside change could not be merged (`pending-intake-failed`), the next edit or the idle save within a few minutes saves it (`retryWhen: next-save`). When OpenKnowledge has no agreed version of the file to merge with (`pending-intake-failed-no-base`, or any hold on such a document), the edit is not saved: the next edit to the document replaces it with the file on disk and moves the held edit to the document history (`retryWhen: replaced-on-next-edit`); re-read after that and re-apply the edit if it is still needed. When merging raised a conflict (`pending-conflict`), it is saved after the user resolves the conflict in the app (`conflict-resolved`). In every case, do not repeat the write now: re-read the document before editing it further.

A write to a Mermaid, Excalidraw or plain-text document or to a global or external skill returns its ordinary success response whatever its save does; these writes never return `save-held`. The save compares the file the same way, and what happens shows only in the document, its history and the user's notice. A Mermaid, Excalidraw or plain-text file has no merge: when it changed outside OpenKnowledge, the version being written is kept and the outside version is saved to the document's history. A skill merges an outside change like a Markdown document, and when the merge is refused the version being written is kept and the outside version is saved the same way. When history cannot take a version, it is saved under `~/.ok/edit-backups/discarded/` instead. When neither can take it, or the file keeps changing, cannot be read, or changed to text that is not UTF-8, nothing is written: the save is held and retried, and only the user's notice says so. So after a write to one of these files, re-read it before editing it further, and if it is not what you wrote, look for the other version with `history`. A typed outcome for these writes is planned. Settings files, which the `config` tool reads, follow the same rules when they change outside OpenKnowledge: a valid outside version replaces the user's unsaved settings edits, which are saved first, as soon as OpenKnowledge sees it; an invalid one is only rejected until the next settings save, which saves it to history, or the backup folder, and then writes over it.

`conflict.kind` says where the conflict came from, and the kind decides what a resolve does. `merge-native` is a git merge that left unmerged stages in the index. Resolving one stages your choice with git and commits the merge once no `merge-native` conflict is left. `working-tree` is a pull-only overlay collision, pinned to the origin blob it hit. `reconcile` is OpenKnowledge's own three-way merge of the editor against disk, including protected stale saves; no git object holds those stages, so OpenKnowledge snapshots them when it detects the conflict. Resolving a `working-tree` or `reconcile` conflict commits nothing.

A `reconcile` conflict also carries a `reason`: `refused-conflict-markers`, `refused-no-base`, `refused-too-large`, `disk-markers`, or `stale-external-write`; `merged-with-markers` appears only on entries recorded by earlier versions, or when both kept versions could not be applied to the open document. On `stale-external-write` the compatibility field `conflictKind` is `stale-external-write`. Every other row uses `conflictKind: "git"`. An outside edit to the same block as unsaved edits is not a conflict: both versions are kept in the document. `refused-too-large` means a merge past the size cap or one that failed OpenKnowledge's fidelity check, and is raised only when the outside version could not be saved to history; otherwise the OpenKnowledge version stays and the outside version goes to the document's history. The server log names the failed check.

A write to a document whose file was deleted, renamed or moved on disk returns `urn:ok:error:doc-removed` (409): the edit reached collaborative state, but the disk write was refused. Retrying the same write does not help, and the `detail` says which case applies. If the file was deleted, re-create the document with `write` if you still want the content. If it was renamed or moved and the edit did not move with it, because it reached the document after the move or OpenKnowledge could not carry it, the `detail` names the new path: re-read the document there and re-apply your change. If a different file now sits at the old path and has not been loaded into the document, only a reload of that document from disk clears the refusal, so tell the user instead of retrying.

When OpenKnowledge follows a rename or move made outside the app, it carries the document's text, with every edit it already held, to the new name. A write whose disk save was still pending waits for that to finish, then returns `urn:ok:error:doc-moved` (409) if its edit was carried, and the `detail` names the new name: the edit is saved there, so do not repeat it; re-read the document at its new name. If the edit was not carried, the write returns `urn:ok:error:doc-removed` as described above. Waiting for the carry counts toward the same 20 seconds as the rest of the write. If the carry has not finished when they run out, the write returns success before its disk save and no error follows: the edit goes wherever the carry takes it, to the new name or, if the carry fails, to the document's history. Re-read the document at its new name to confirm. While the file of an open document is missing, OpenKnowledge holds the document for a re-check of the folder, in case the file was moved rather than deleted, and a write's disk save waits up to 20 seconds for that to settle. If OpenKnowledge then follows a move, the write returns `urn:ok:error:doc-moved` or `urn:ok:error:doc-removed` by the same rule. If the delete stands, the write returns `urn:ok:error:doc-removed` (409) and the `detail` says the edit went to the document's history, not to disk; re-create the document with `write` if you still want the content. If OpenKnowledge stops while the file is still missing, the write returns `urn:ok:error:server-stopped` (503) and the edit is in the document's history. A hold can last up to 30 seconds. If it is still unresolved when the write's 20 seconds run out, the write returns success before its disk save, so that success does not confirm the edit is on disk: the edit goes wherever the hold resolves, to the new name or to the document's history, and no error follows. Re-read the document to confirm, and if it is gone, look for it under a new name or in its history.

A write whose document path cannot be resolved inside the content directory returns `urn:ok:error:path-escape` (400): the edit reached collaborative state, but the disk write was refused. This covers a symlink cycle at the document's own path, a link resolving outside the content directory, and a link resolving into a `.git` folder, an OpenKnowledge config folder itself, or its machine-local state. It is not retryable — repair the path on disk before writing this content again.

A write refused because the document's duplication baseline could not be read at the final disk flush returns `urn:ok:error:store-refused` (503): the edit reached collaborative state, but the disk write was refused rather than risk persisting duplicated content. The document file was not updated; the server preserves the edited document, with a copy in its recovery buffer unless that buffer is unavailable or unwritable. Retry only after the filesystem fault is repaired.

A write that arrives while Git is updating the project's `HEAD` or index waits for that to finish and then applies to the checked-out content. That covers a branch switch, a commit, a merge or a reset, and also index-only activity such as `git add` or a `git status` that refreshes the index. Fetching from the remote during sync does not hold writes back; a disk save that sync deferred completes when sync finishes. A request waits at most 20 seconds in total, however many documents it writes. If a branch switch starts while a write's disk save is still pending, the write returns `urn:ok:error:branch-switched` (409): the edit stays in the open document, merged with the checked-out branch's version of the file the way an outside edit is, and is saved with the document's next save. Do not repeat it; re-read the document to confirm. `POST /api/agent-write-batch` reports this per entry inside its `200` envelope. `restore_version` skips the wait before applying, but its confirmation of the disk save can still wait under the same cap, and it can return the same error. If any of that Git activity is still running when the 20 seconds run out, the write applies anyway and its success response can arrive before the disk save, so that response does not confirm the edit is on disk.

A whole-document replace attempted while another writer changed the same document in the last few seconds returns `urn:ok:error:concurrent-overwrite-refused` (409): nothing was written, so there is no partial edit to undo. This is not tracked conflict state, so there is nothing to resolve. A single-document HTTP response carries `retryAfterSeconds` alongside a matching `Retry-After` header, and the `write` tool appends the same bound to its error text (`Retry after 3s.`). After whole-request schema validation succeeds, `POST /api/agent-write-batch` keeps its `200` success envelope; each concurrent-overwrite refusal carries the problem type and `retryAfterSeconds`, while sibling entries are unaffected. Invalid input instead rejects the whole request before processing. Wait that long and repeat the write, or use `position: "append"` or `"prepend"`, or `edit`, which bypass concurrent-overwrite protection but still require valid input. Peer writers are distinguished by identity. Anyone supplying an `agentId` or `x-ok-connection-id` must use a stable value unique to one writer, containing only ASCII `[A-Za-z0-9_-]` characters and 1–64 characters long. A nonconforming `agentId` is discarded: `POST /api/agent-write-md` and `POST /api/agent-write-batch` then treat the caller as unidentified, while `POST /api/lint/fix` falls back to the project [principal](./what-open-knowledge-writes.mdx) when available. A nonconforming `x-ok-connection-id` is silently replaced with a minted identity. A `POST /api/agent-write-md` caller sends its `agentId` on every write. The MCP write tools declare no `agentId` field. OpenKnowledge mints an identity per MCP connection unless an MCP Streamable HTTP client forwards a valid `x-ok-connection-id` while creating the protocol session. Writers that share or reuse an identity share [writer attribution](./core-concepts.md#attribution-and-collaboration), the server-side write session, and undo history, and are not refused against each other; the server does not detect identity collisions. Having an identity records you as a peer, so a `replace` carrying a different identity is refused for the next few seconds, while your own recent write does not arm the refusal against your follow-up `replace`. A writer that has no identity of its own is never recorded as a peer, so it never arms the refusal against a later writer. That covers a `POST /api/agent-write-md` that omits `agentId`, and a `lint` fix that both omits `agentId` and runs on a project with no principal. A caller that sent no `agentId` is still refused its own `replace` when a writer that did send one changed the document in the last few seconds, because that caller cannot be shown to be the recorded writer. Two `POST /api/agent-write-md` callers that both omit `agentId` are never refused against each other, though a recent change from a connected editor still refuses both of them.

A body or frontmatter edit addressed to a path with no document returns `urn:ok:error:doc-not-found` (404) from `POST /api/agent-patch` and `POST /api/frontmatter-patch`: nothing was written or created, and the body carries `committed: false`. Paths are relative to the content root. The problem body lists up to three likely targets in `candidates` (a folder's hub document, or documents whose trailing path segments match), and the title names them. A find that misses inside an existing document is a different error, `urn:ok:error:target-not-found`.

A write refused because the server is at its limit of concurrent agent write sessions returns `urn:ok:error:too-many-agent-sessions` (503): nothing was written, so it is safe to repeat. The problem body says so in `detail`, carries `committed: false`, and carries `retryAfterSeconds` alongside a matching `Retry-After` header. `POST /api/agent-write-md`, `POST /api/agent-patch`, `POST /api/frontmatter-patch` and `POST /api/lint/fix` answer this way, and the `write`, `edit` and `lint` fix tools append the detail and the bound to their error text (`Retry after 10s.`). `POST /api/agent-write-batch` keeps its `200` success envelope; each refused entry carries the problem type, `detail`, `committed: false` and `retryAfterSeconds` in its `error`, while sibling entries are unaffected. Wait that long and repeat the request. A `write` from a `template` creates the document before it patches the frontmatter, so when only that patch is refused the tool says so and the document already exists: apply the frontmatter with `edit` instead of repeating the `write`. For any other frontmatter failure on that path, re-read the document before changing it, because the patch may have been applied.

### Resolving a conflict

The MCP server has no conflict tools. An agent that hits `doc-in-conflict` or `stale-external-write` should name the file and ask the user to resolve it in the app; see [Resolving a conflict](../features/git/sync.mdx#resolving-a-conflict). HTTP integrations can list conflicts with `GET /api/sync/conflicts`, then read `GET /api/sync/conflict-content?file=<path>` for `base`, `ours`, `theirs`, the conflict kind, and its current `resolutionOptions`. To resolve one, send `POST /api/sync/resolve-conflict` with `{ file, strategy }`, choosing an offered strategy (`mine`, `theirs`, `content`, or `delete`). The `content` strategy also requires `content`; an empty string keeps an empty file. Content must be free of conflict markers. Use only the strategies returned for that conflict; its kind determines the commit behavior described above.

## Preview links

Read and write tools return a `previewUrl` for any doc they touched, but **those are route-only** (`/#/<doc>` with no host:port), meant to identify the doc, not to be opened as-is. Hosts that want to open the editor (Claude Code Desktop's `preview_start({url})`, terminal `open <url>`) call `preview_url` to resolve the full URL once per session.

`preview_url` always carries an `autoOpen` boolean (top-level on its response) reflecting the user's [`appearance.preview.autoOpen`](./configuration.mdx) preference. The write tools (`write`, `edit`) carry the same boolean on the `warning` object, which fires only when no browser is attached to the preview. In the common case (a browser is attached), the write response has no `warning` and no `autoOpen` field. Agents honor `autoOpen` before navigating: `true` (default) follows the host-capability routing in the bundled skill; `false` means the user is managing their own preview window, so the agent surfaces the URL on request but does not open or refresh anything. The value is resolved fresh on every tool call, so a mid-session toggle propagates within 0–1 calls, with no client restart.

## Refresh agent guidance

Update the OpenKnowledge build that serves your MCP connection. If you use the desktop app, update that app; on macOS, the CLI can use its bundled server and skills, so updating only the npm package can leave the desktop's older guidance in use. For a standalone CLI installation, update the CLI.

Then run `ok init` in the project, or turn its editor integration off and on in **Settings → Agent connections**. Reconnect the agent client to load the updated tools and project skill.

In-app agents refresh their bundled skill when a new thread starts. The Claude Code plugin starts OpenKnowledge through `npx @inkeep/open-knowledge@latest mcp` and does not bundle a skill; refresh project guidance with the steps above. `ok repair-skills` repairs user-global bundles and restores missing project copies, but preserves an existing project skill; use the steps above to refresh that copy.
